# bvm-lang v2.0.0-alpha.1 — The LSB Virtual Machine

**A new major version, as a pre-release.** bvm-lang 2.0 executes LSB, the
LexerSketch bytecode of `bytecode-lang`: the one instruction set every
LexerSketch tier agrees on. Version 1's own small `Op`/`Chunk` instruction set
is gone. alpha.1 runs every LSB instruction except the coroutine group, which
arrives in alpha.2; the API freezes at 2.0.0 once a real consumer (Mox) has
run on it.

## What is bvm-lang?

The T1 tier of LexerSketch (ARCHITECTURE §7): the default interpreter every
language built with the `-lang` family runs on before (or instead of) native
compilation. One VM serves static languages, through typed registers and
unboxed arithmetic, and dynamic ones, through `dyn` registers, PHP-style
ordered maps, and hooks a language uses to supply its own semantics. It is an
LXRT-tier crate depending only on `bytecode-lang`.

## What's new in 2.0.0-alpha.1

### Load, then run

`Program::load` takes a `bytecode_lang::Module` (or `Program::decode` its
bytes) and checks, in one pass, every fact the interpreter indexes by:
register operands and call windows, every table index, every branch target,
arities, type operands, `promote` placement, handlers, inheritance, constant
nesting, hook signatures. Imports bind to functions registered in a `Host`.
A `Vm` then runs functions with `Value` arguments:

```rust
use bvm_lang::{Host, Program, Value, Vm};
use bytecode_lang::{Inst, IntOp, IntTy, ModuleBuilder, ValType};

let mut m = ModuleBuilder::new();
let mut f = m.function("mul", &[ValType::I64, ValType::I64], &[ValType::I64]);
let r = f.reg(ValType::I64);
f.emit(Inst::IMul { dst: r, lhs: f.param(0), rhs: f.param(1), op: IntOp::new(IntTy::I64) });
f.ret(r);
let mul = m.add_function(f).unwrap();
let program = Program::load(m.finish().unwrap(), &Host::new()).unwrap();
assert_eq!(Vm::new(&program).run(mul, &[Value::Int(6), Value::Int(7)]), Ok(Value::Int(42)));
```

### The instruction set

Moves, typed and dynamic constants (aggregates materialised once and shared
copy-on-write), globals; every OPS integer operation at every integer type
under every overflow, division-by-zero, shift, and float-conversion policy;
IEEE float arithmetic with correctly rounded `sqrt` and `fma` and the IEEE
`remainder`; conversions; the dynamic numeric fast path with PHP's
`promote` (`PHP_INT_MAX + 1` is `9.223372036854775808e18`, `7 / 2` is `3.5`)
and CPython's float floor division; dynamic comparison, truthiness,
concatenation, type tests and casts, indexing, properties (fields, inherited
methods, string-keyed maps), dynamic calls, and iteration; every hook;
branches, `switch`, direct, indirect, host, and tail calls; exceptions;
closures and cells; structs; arrays; maps; iterators; `dup`; byte strings.

### PHP arrays

Maps keep insertion order, update in place, track the next integer key
across deletions (PHP 8.3 rules, negative keys included), and iterate the
live map. Lists stay *packed* (no hash index) until a key breaks the
`0, 1, 2, ...` pattern. `dup` is O(1) and copies on the first write.

### Exceptions and `finally`

Handler regions, errors crossing frames, and precise unwind points: a
failing instruction never writes its destination. The canonical `finally`
lowering from LSB §4.3 is tested end to end, including a `return` in
`finally` overriding a pending throw and an error in `finally` replacing it.

### Budgets (ISSUES H09) and locations (M62)

`Limits` sets fuel, heap bytes, call depth, and register-stack slots. Fuel is
charged at safepoints, calls, hook invocations, taken backward branches, and
handler entries, so even a module with no safepoints cannot run forever.
`VmError` carries the OPS/LSB error code, the function, and the pc, and
`Program::location` maps them to the source through the line table.

### Memory

A heap with exact roots, an iterative mark and sweep rationed by allocation
volume, generation-checked handles that read as `nil` once stale, and slots
retired before their generation could wrap. Why not `gc-lang` 1: its handles
cannot live in a 64-bit register next to floats and ints, and it has no byte
accounting for the memory budget (details in `dev/ROADMAP.md`).

## Breaking changes from 1.0

The instruction set (`Op`, `Chunk`, `Reg`, `Const`, `Addr`), the value-lang
`Value` re-exports, `Vm::with_capacity`, the 1.x `VmError` variants, and the
`serde` feature are removed. The CHANGELOG has a full migration table; LSB
§11 maps every 1.x instruction to LSB.

## Not in this release

- **Coroutines** (`coro_new` .. `coro_result`, `0xF0`..=`0xFC`): modules with
  them load; a run that reaches one ends with `VmError::Unsupported` naming the
  opcode and pc. alpha.2.
- The verifier's type discipline (bytecode-lang 0.5): ill-typed modules load
  and compute garbage or raise `TypeError`; they cannot escape the VM.
- Host functions calling back into bytecode (host-lang).

## Quality

Tests: per-instruction conformance suites; the OPS conformance table (every
operation x every policy x edge values x every integer type, every float
operation over IEEE edge values, and the dynamic path under every policy
including `promote`) against an `i128` reference in the test; differential
property tests of random straight-line and branching programs against a
reference interpreter, comparing the whole register file and the fuel used
(mutation-checked); PHP-array properties against a model; exception, budget,
GC, and loader suites; fuzz properties over random code and mutated
encodings; property tests of the software float routines against `std`.

Benchmarks (`cargo bench --bench bench`) cover dispatch, calls, maps,
strings, GC churn, and loading; see the README for the current numbers and
the comparison with 1.0's dispatch loop.
