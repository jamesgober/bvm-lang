# bvm-lang v2.0.0-alpha.4 — The Reference-Counting Memory Profile

**PHP's memory model, as a second profile.** A VM made with
`Vm::with_memory(&program, Memory::Rc)` counts references and collects
garbage cycles by trial deletion, as PHP does: an object dies at its last
reference, before the next instruction, so a destructor named with
`Vm::set_destructor` runs where PHP runs `__destruct`, a dropped generator
closes where PHP destroys it, and copying an array drops a PHP reference
nothing else holds (LSB §5.17's documented divergence, closed at run time).
The tracing profile stays the default and behaves as before; its speed is
measured below (two small slowdowns remain).
Dynamic-call binding is now fuel-proportional. Still a pre-release: the API
freezes at 2.0.0 once a real consumer (Mox) has run on it.

## What is bvm-lang?

The T1 tier of the toolchain (ARCHITECTURE §7): the default interpreter every
language built with the `-lang` family runs on before (or instead of) native
compilation. One VM serves static languages, through typed registers and
unboxed arithmetic, and dynamic ones, through `dyn` registers, PHP-style
ordered maps, and hooks. It is an LXRT-tier crate depending only on
`bytecode-lang`.

## What's new in 2.0.0-alpha.4

### Two memory profiles (DECISIONS D22)

`Memory::Tracing` (the default; `[runtime] memory = "gc"`) and `Memory::Rc`
(`[runtime] memory = "rc"`). LSB format 2 has no module flag for the
profile, so the runner chooses it when it makes the VM; the profile is fixed
for the VM's life. Everything a program computes is the same under both,
except what LSB lets a reference-counted runtime do differently:

| | `Memory::Tracing` | `Memory::Rc` |
|---|---|---|
| Freeing | mark and sweep after enough allocation | at the last reference, before the next instruction |
| Garbage cycles | traced | trial deletion when 10,000 possible roots are buffered, fuel-charged |
| Dropped suspended coroutine | closed at the next fuel charge point after a collection finds it | closed at the last reference |
| Destructors | after a collection finds the object | at the last reference (PHP's timing) |
| Copying contents holding a reference only they hold | the copy shares it (LSB) | the copy holds the value (PHP) |

### Reference counting without pointers

Counts live in the existing generation-checked slots (in padding: the slot
did not grow) and are kept at every store of a counted location: the
reference-typed registers of live and suspended frames, frame closures,
object slots, array and map storage (once, however many containers share
it), globals, caches, the resume chain, the scheduler, and values handed to
the host (held until the next run, the profile's version of "valid until
the next run"). The crate stays `#![forbid(unsafe_code)]`.

A count reaching zero never frees anything mid-instruction: the object
waits on a list the VM settles before the next instruction. That is where
objects die, in PHP's order (a function's variables in declaration order,
an array's elements first to last, an object before what it holds), where
destructors and drop-closes start, and why no word an instruction holds can
go stale. Freeing is iterative: a million-node chain is freed in one go
without recursion. Objects that die together are destructed one after
another, never nested inside each other; what a destructor drops is
destructed inside it, as in PHP.

A count that would pass `u32::MAX` sticks: the object is never freed again,
and the run ends with the `OutOfMemory` trap at the next instruction
boundary. No undefined behaviour and no panic.

### The cycle collector

Synchronous trial deletion (Bacon and Rajan, the algorithm PHP's
`gc_collect_cycles` uses): mark gray what the possible roots reach while
subtracting internal references, restore what something outside still
holds, free the rest. Array and map storage shared copy-on-write between
containers is a node of its own, so cycles through `dup`ed containers are
found. Every phase uses work lists, so a million-node ring is collected
without recursion. PHP's adaptive threshold keeps a program whose roots are
all live from making every collection a wasted one, and the collector
charges one unit of fuel per 64 objects it visits, so its work is bounded
by the run's budget. Garbage that needs code (a destructor, a suspended
coroutine) is kept, with what it reaches, until that code has run, and is
freed by the next collection. `collect_garbage` runs a full collection.

### Destructors, in both profiles

`Vm::set_destructor("__destruct")` makes a struct type's method of that
name (its own or inherited) its destructor, called with the instance when
it dies: at the last reference under RC, after the collection that finds it
under tracing (through the finalization queue dropped coroutines use). At
most once per object; its result and errors are discarded; it is charged
fuel; one the limits cannot hold is skipped. `VmError::BadDestructor`
reports a method that cannot take the instance as its one argument.

### PHP's reference unbinding (ISSUES P34, runtime side)

Under RC every copy of contents (the copy-on-write copy a write makes, and
`dup` of a struct, PHP's `clone`) turns a reference slot whose reference
only the copied contents hold into a plain slot of its value, exactly
`zend_array_dup`'s rule; a write through such a slot of shared contents
copies first, as PHP's `SEPARATE_ARRAY` does. `foreach ($a as &$v) {} $b =
$a; $b[0] = 7; $b[2] = 9;` leaves `$a` as `[1, 2, 9]`, PHP's answer, without
the code generator emitting `dunref` (bcgen-lang 0.3 does not).

### Fuel-proportional binding (ISSUES P33)

Calls with named arguments bind through a hashed name index built at load
time (for lists of more than eight named parameters), with an ordered set
for names repeated in a rest collection: a hostile named spread of 200,000
keys into a 200-parameter list binds in time linear in its size, where
`ParamList::bind`'s scan made it 200 times longer. A call of `n >= 64`
flattened items is charged `n / 64` more units before binding. An empty rest
parameter shares one empty storage until its first write. Both binders are
property-tested against `ParamList::bind`.

## Breaking changes from alpha.3

- A dynamic call of 64 or more flattened items costs `n / 64` more fuel
  units (before binding, so binding errors after a large flattening are
  charged them). Calls of fewer items are charged as before.
- `VmError` gains `BadDestructor(FuncId)` (`#[non_exhaustive]`).

Nothing changes for a host that keeps `Vm::new` and does not name a
destructor.

## Proposed for LSB (recorded in the ROADMAP; LSB was not edited)

- A module-level memory profile and destructor method, once LSB carries
  runtime metadata (today the runner chooses both).
- D22's "specified per profile in LSB": destructor timing, and reference
  unbinding on copy in §5.17, written per profile.
- §5.14: the two new charges (`n / 64` per large dynamic call; one per 64
  objects the RC cycle collector visits).

## Known limitations

- Errors escaping a destructor are discarded, as LSB §5.13 rule 13 does for
  drop-closes; PHP raises them where the object died.
- Objects still reachable when a VM is dropped are not destructed (PHP's
  shutdown pass is the host's call: let go, `collect_garbage`,
  `run_finalizers`).
- Destructor timing follows register reuse: a dead register still holding
  an object keeps it until overwritten or until its function returns, where
  PHP frees temporaries at once.
- A program that builds a long chain one node at a time fills the
  possible-roots buffer as it goes, so the collector walks the chain several
  times (O(n^1.5) in all, fuel-charged), as PHP's does.
- Separation and copy-on-write decisions use LSB §5.16's bits in both
  profiles. LSB would allow RC to decide with counts; that was built first
  and diverged from tracing on generated code that stores a container
  without `dup`, so it was dropped (counts decide only whether a copy is
  physical).
- `[runtime] cycles = "leak"` (LSF2) is not exposed.

## Quality

New suites: `tests/memory_rc.rs` (26 tests: PHP's destructor order for
reassignment, `unset`, scope exit, element overwrite, array and nested
destruction, resurrection, destructor errors, traps, fuel, and depth;
cycles at the collection point and from the automatic collector inside a
run; tracing destructors; inherited and invalid destructors; close on drop
at the last reference; unbinding for arrays, `foreach` by reference, maps,
and `clone`; a cycle through shared storage; million-node rings and chains;
the collector's fuel; the memory budget; host values), `tests/binding.rs`
(3: per-item fuel from 0 to 6,400 items, a 200,000-key hostile named
spread, empty rests). The whole-module differential properties run under
RC too (6,000 random programs per run against the reference interpreters,
with exact live-object parity against tracing once collected and a guard
that at least 95% of programs are compared; 60,000 more random programs
were run while preparing the release), and the untrusted-input fuzzing
covers both profiles with random destructors. In debug builds every RC run
recounts every count from its holders when it ends, and every RC
collection checks that it kept nothing unreachable. The whole existing
suite was also run with RC forced as the default: only the tests that
assert tracing timing differ.

Mutation checks: a removed increment and a removed closure release were
each caught by the debug recount (which names the slot and kind); the named
binder's duplicate check and cursor advance were each caught by its
property. Caught during development rather than by deliberate mutation:
destructors of sibling objects nesting (fixed by the zero-list floors, now
pinned by the order tests), queued finalizations nesting 10,000 deep (now
pinned by the depth test), and one real design problem found by the RC
differential (count-based separation, above). A `dup`-heavy loop's memory
budget depends on rationed recounts; a test fails without them.

Totals with all features: 47 unit tests, 288 integration tests in 20
files, and 108 doctests (443; 442 without default features).

## Performance

Criterion, one run, Windows x86_64 on a machine shared with other builds
(indicative only; the README has the full table):

| Workload | `Memory::Tracing` | `Memory::Rc` | RC / tracing |
|---|---:|---:|---:|
| `fib25` | ~4.0-4.1 ms | ~6.5-6.9 ms | ~1.6x |
| `dyn_loop5_100k` | ~0.63-0.74 ms | ~0.74-0.78 ms | ~1.1x |
| `nested_append_100k` | ~6.7-7.0 ms | ~7.9-8.8 ms | ~1.2x |
| `alloc_1m_live_10k` | ~87-102 ms | ~121-136 ms | ~1.35x |
| `generator_iter_100k` | ~4.9-5.0 ms | ~9.1-10.1 ms | ~2x |
| `destructors_100k` | ~6.4-6.5 ms | ~12.9-13.5 ms | ~2x |
| `cycles_100k` | ~3.9-4.2 ms | ~13.0-13.6 ms | ~3.4x |

RC is slower everywhere; it buys PHP's timing, not speed, which is why
tracing stays the default.

The tracing profile against alpha.3, measured with an alternating harness
(minimum per process, four rounds; criterion's intervals on this machine
move by tens of percent): `fib(25)` ~8% faster, `dyn_loop5`, generators,
nested append, and `alloc_1m_live_10k` at parity (within ~3%),
`create_finish` ~1% slower, `map/int_keys` ~4% slower, and
`foreach_by_ref` ~5-8% slower. The last two are not yet recovered.

The P33 hostile case, one named spread of 200,000 keys into 200 named
parameters and a named rest, runs in ~126-136 ms including the host
building the map (`call/dcall_spread_named_200k`).
